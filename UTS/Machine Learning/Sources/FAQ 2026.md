# 1. Can I use library A | dataset B?

This is one of the most asked questions about the project.

## The short answer

Using particular tools/resources is independent of whether your project is eligible. The principle is that the project must contain real learning effort on your part. A library call is acceptable when it saves you from work that is NOT within your study scope (and you would not claim credit from), e.g. a procedure you have already understood or one that is of a lower technical level (details below). It is not acceptable when it performs the work that essentially defines the learning objective of the project.

So the question to ask is not "is this library allowed". It is "which part of this project am I supposed to be learning from, and does this call take that part away from me".

## If you chose Option 1: implementing the algorithm

Here the thing you are learning is the algorithm itself.

You may use library functions for the underlying numerical machinery. Matrix multiplication, solving a linear system, matrix decomposition, eigenvalue computation, random number generation, sorting, array reshaping and broadcasting are all fine. numpy, scipy for linear algebra, pandas for loading and organising data, and matplotlib for plotting are all fine. It is not expected for you to write your own triple loop for a matrix product.

You may not call a library that performs a step of the algorithm for you. scikit-learn, PyTorch, TensorFlow, Keras, XGBoost, LightGBM and anything equivalent are out for the algorithm you chose to implement.

There are spaces in between these two extremes. You may use a library for a subroutine that is not the focus of the algorithm, e.g. an off-the-shelf optimiser, an off-the-shelf splitting criterion, an off-the-shelf distance-and-vote routine. Such options are of your choice — the deeper you explore by yourself, the more you will learn and the higher your marks can be.

BTW, it is a good idea to compare your implementation against an available library, and use these libraries as a reference to check your own implementation. Doing so is encouraged, and how you handle the comparison is itself worth marks. See below.

You are expected to use AI assistance while you build this. That is not a concession, it is the assumption. What you are marked on is not whether you typed the code unaided. It is whether you finished the process understanding the algorithm.

### What understanding looks like when it is tested

"I understand it" is not a claim we take on trust, and it is not established by simply running the code demo by one-click. It is established by what you can do with the algorithm once it is written. In the presentation, the following aspects are often checked:

**The formula and the code line up in both directions:** Every symbol in the update rule or the objective can be pointed to in your code, and every non-trivial line of your code can be pointed back to the mathematics. Include an explicit mapping in your report. If a line exists only because the code broke without it, say so and explain what it is compensating for. That is a legitimate and interesting thing to report.

**You can say why each step is there:** If the answer to "why do you subtract the mean here" is "because that is what the equation says", the step is not yet understood. The answer should be about what that piece does in the "big picture", e.g. by explaining how things can go wrong without.

**You can predict the effect of a change before you run it:** Take one component of your implementation, decide in advance what breaking it will do, break it, and check. Flip the sign of the update. Remove the regularisation term. Fix the learning rate at something far too large. Feed in features on wildly different scales. Write down the prediction first, then the observed result, then reconcile the two. A prediction that turned out wrong, followed by a correct diagnosis of why, tells much about your understanding of the project.

**You can account for the difference against a reference implementation:** Run the library version on the same data. Matching to a few decimal places is a good sign. More desirable: to explain the residual gap: different initialisation, different stopping rule, a regularisation constant applied on a different scale, a different convention for the intercept. It is common that our crude implementation differs from a polished library, and you can often learn a lot by explaining it.

**You can check your derivatives numerically:** If your algorithm involves a gradient you derived, compare it against a finite-difference estimate at a few random points and report the agreement. This takes about ten lines and catches the single most common class of silent error.

**You know what each part costs:** State the time and memory complexity per iteration in terms of the number of samples, features and iterations, then measure the actual runtime as you scale one of them and show that the measurement follows the stated order. Where it does not, explain what dominates instead.

**You know when it fails:** A singular or near-singular matrix, one class absent from a fold, perfectly correlated features, a feature with zero variance, a sample size below the feature count. Find the ones that apply to yours, show what happens, and say whether you handled it or chose to let it fail loudly.

**You know what it assumes:** State the assumptions the algorithm makes about the data, then construct or find data that violates one of them and show the consequence. This is the difference between knowing the procedure and knowing the method.

You will not have room to do all of these well. Choose the ones that are informative for the algorithm you picked, and do those properly. Depth on four of these beats a sentence on each of eight.

## If you chose Option 2: applying the algorithm

Here the thing you are learning is what happens at the join between an algorithm and a real problem, so the algorithm is not what you must write. Use whatever libraries you like, including all the ones ruled out above. Calling fit is not the part you are being marked on, and re-implementing it would spend your effort in the wrong place.

The effort has to go into i) adapting the algorithm to data it may not be straightforwardly directly designed for, ii) establishing that the approach is feasible, and iii) establishing that the result is reliable. A submission that loads a clean dataset, calls fit, reports an accuracy figure and stops has done none of the three and will be marked accordingly.

### Adapting the algorithm to the data

Real data violates the assumptions that made the algorithm work in the lecture. Your job is to find which assumption your data breaks and do something defensible about it.

Name the specific mismatch rather than the general category. Not "the data was messy" but: the classes are at 200 to 1 so the majority-class predictor already scores 99.5 percent and accuracy is therefore uninformative here. Not "there were missing values" but: this sensor is absent whenever the machine is off, so missingness carries the signal and imputing it destroys the very thing that predicts the outcome.

Then say what you changed and why that change rather than an alternative. Adaptation rarely has a single natural choice. There may be competing options, and choosing between them with a stated reason is the work. E.g. resampling versus class weights versus moving the decision threshold are three different answers to imbalance with three different consequences, and picking one silently is the thing to avoid.

Then say where the fit is still imperfect. There is almost always a gap between what the problem cares about and what the objective function optimises. The domain may care much more about one direction of error than the other while the loss treats them alike. The domain may care about a decision at the level of a customer while the rows are transactions. Identifying that gap is valuable.

### Establishing feasibility

Feasibility means the approach could actually be used for the purpose. E.g. establish that the inputs exist when the prediction would have to be made. I.e. the solution does NOT make a loopy information pathway. Or in more technical terms, that the features are not "leakage" features, e.g. a field recorded at the same time as the outcome, or updated after it, will give you an excellent score and a useless model. Walk through your features and state, for each suspect one, when its value becomes known.

Establish that the cost is acceptable at the scale the problem actually has. Measure training time and memory at the size you have, state how they grow, and extrapolate to the size the application would have. If prediction has to happen while a user waits, measure the per-item latency and compare it with the budget.

Establish that it beats what it would replace. Every real setting already has an incumbent, usually a simple rule or a human. Construct the corresponding baseline and compare against it. A model that is worse than a two-line rule is a finding worth reporting, and reporting it is a better submission than hiding it.

### Establishing reliability

Reliability means your number would survive contact with data you have not seen.

Design the validation to match the way the thing would be used. If the data has a time order and the use is prediction of the future, split by time. If rows are grouped by patient, user or device, split by group, because a random split puts the same subject on both sides and inflates the score. State which structure your data has and which split you therefore chose.

Report variation, not only a point estimate. Repeat across folds and seeds and give the spread.

Show sensitivity to your own choices. You made decisions about preprocessing, encoding, thresholds and hyperparameters. Vary the two or three that you think matter most and show whether the conclusion holds. A conclusion that survives is worth stating; one that does not is worth knowing about.

Look at the groups, not only the average. Break the error down by class, by segment, by the slices a user of this system would care about. Aggregate performance routinely hides a subgroup where the model is useless.

Say what happens when it is wrong. Choose an operating point and justify it in terms of the relative cost of the two error types in this setting. Say how an out-of-range or unfamiliar input would be noticed. Say what would cause performance to decay after deployment and how you would detect it. You are not required to build any of this. You are required to have thought it through concretely enough to describe it.

## How this connects to marks

High marks in this subject go to work that shows sustained, demanding effort along one of two directions. You do not need both, and attempting both usually produces two shallow halves.

The inward direction is depth into the algorithm itself: its mechanism, its mathematics, its failure behaviour, its cost, why it does what it does. This is the natural direction for Option 1.

The outward direction is reach beyond where the algorithm is normally applied: a domain it is not usually used in, data it was not built for, a method adapted or combined to make it fit, an analysis that establishes whether it can be trusted there. This is the natural direction for Option 2.

What does not earn high marks is the safe middle: a standard algorithm on a standard dataset with a standard split, correctly executed, with nothing difficult attempted in either direction. That work is not wrong, and it will pass. But it does not demonstrate anything beyond the ability to follow the procedure taught in class.

Choose one direction, go as far along it as your time allows, and report honestly what you found, including what did not work.
