# Conditions for Machine Learning

Now that we have a rough idea of what is Machine Learning and its working mechanism. A natural question in practice is: when is using ML appropriate? In which scenarios/conditions is ML a good idea? Conversely, what are the risks of using ML? How to identify the missing conditions before engaging in a project to build a data-driven solution?

## When to Use ML?

Machine Learning is a powerful tool -- it often effectively replaces "coding algorithms" with "collecting data." This is often computationally expensive and, as discussed, lacks interpretability. Therefore, ML should only be employed when specific conditions are met.

## The Three Basic Conditions

- **A Pattern Exists (The Task is Mechanical)**

There must be an underlying relationship between the inputs and outputs. We can generally tell if a task is "mechanical" if a human can "get the point" after seeing examples.

*Example:* Identifying a face from the pixels of an image.
- *Counter-example:* Predicting the next outcome of a fair die roll. (There is no pattern to learn; it is pure noise).

- **Data is Available**

Since the logic is constructed from examples, we must have a sufficient volume of examples. The "experience" \(\mathcal{E}\) is the fuel for the process.

*Requirement:* We need input-output pairs \(\{(x,y)\}\) where the distribution of \(x\) covers the scenarios we expect to encounter in deployment.

- **We Cannot Pin It Down Mathematically**

The rules governing the pattern should NOT be straightforward to be written down explicitly. If we know the governing equations (e.g., calculating the trajectory of a ballistic missile), it is usually more efficient to use them to explicitly program a computer to perform the task. ML is for when the "rules" are intuitive and non-explicit.

*Example:* Detecting sarcasm in text / spam in an email.
- *Counter-example:* Sorting a list of numbers. (Quicksort is provably correct and efficient; we don't need to "learn" how to sort).

Below are some example scenarios.

#### Scenario 1: Image Classification (Cat Detection)

- **Input (\(\mathcal{X}\)):** A 2D array of pixel intensity values (e.g., a \(224 \times 224 \times 3\) tensor representing RGB color channels).
- **Output (\(\mathcal{Y}\)):** A binary label: "Cat" or "Not Cat".
- **Why ML?**

**Pattern Exists:** There is a consistent visual structure to cats (pointed ears, whiskers, fur texture, facial proportions). Humans can reliably identify cats after seeing enough examples.
- **Data Available:** Millions of labeled images exist (e.g., ImageNet, social media).
- **Cannot Pin Down Mathematically:** You cannot write if (pixel[50][50] > 128 and pixel[100][100] . The relationship between raw pixel values and the concept of "cat" is far too complex and high-dimensional. The pattern exists, but it is implicit in the statistics of millions of pixels across variations in pose, lighting, breed, and background.

#### Scenario 2: Autonomous Driving (Steering Control)

- **Input (\(\mathcal{X}\)):** Sensor readings: camera images (pixel arrays), LiDAR point clouds (3D coordinates of surrounding objects), current speed (scalar), steering angle (scalar).
- **Output (\(\mathcal{Y}\)):** Control commands: steering angle adjustment (continuous value), throttle/brake force (continuous value).
- **Why ML?**

**Pattern Exists:** Safe driving behavior follows patterns—maintain lane position, slow down when the car ahead brakes, avoid obstacles. A human driver learns these patterns through experience.
- **Data Available:** Terabytes of driving logs with sensor inputs paired with human driver actions, or simulated environments.
- **Cannot Pin Down Mathematically:** While the physics of vehicle dynamics is well-understood (you *can* calculate turning radius from steering angle), the decision-making in a cluttered, dynamic environment is intractable. How much should you slow down when a pedestrian *might* step off the curb? When is it safe to merge? These rules are context-dependent and fuzzy. You cannot enumerate all possible traffic scenarios with explicit if-else logic.

#### Scenario 3: Natural Language Processing (Spam Detection)

- **Input (\(\mathcal{X}\)):** A sequence of tokens (words or subwords) representing an email, e.g., ["Congratulations", "you", "have", "won", "$1000", "!"]. Each token is mapped to an index in a vocabulary, so the input is actually a sequence of integers.
- **Output (\(\mathcal{Y}\)):** A binary label: "Spam" or "Not Spam".
- **Why ML?**

**Pattern Exists:** Spam emails share linguistic patterns—urgency ("Act Now!"), financial bait ("You've won!"), suspicious links, poor grammar. Humans can identify spam after seeing enough examples.
- **Data Available:** Millions of emails are labeled by users as spam or not spam (e.g., Gmail's database).
- **Cannot Pin Down Mathematically:** You might try a rule like if ("won" in email and "$" in email): return Spam, but spammers adapt. Legitimate emails also use these words ("You won the employee of the month award!"). The context matters. The relationship between word sequences and intent is subtle and evolves over time. Enumerating all possible linguistic variations is infeasible.

#### Scenario 4: Weather Forecasting (Next-Day Temperature Prediction)

- **Input (\(\mathcal{X}\)):** A time series of meteorological measurements: temperature (scalar), atmospheric pressure (scalar), humidity (scalar), wind speed (vector), cloud cover (scalar), all recorded at hourly intervals over the past 7 days. In total, this might be a vector of dimension \(\sim 7 \times 24 \times 5 = 840\).
- **Output (\(\mathcal{Y}\)):** The temperature 24 hours from now (scalar).
- **Why ML?**

**Pattern Exists:** Weather follows physical laws (thermodynamics, fluid dynamics), and historical patterns exist—pressure drops often precede rain, seasonal trends are consistent.
- **Data Available:** Decades of historical weather records from sensors worldwide.
- **Cannot Pin Down Mathematically (in practice):** While we *do* have the governing equations (Navier-Stokes, heat transfer), solving them for the entire atmosphere at fine resolution is computationally prohibitive for real-time forecasting. ML offers a middle ground: learn an approximate function from the data that captures the essential statistical relationships without solving the full physics at every grid point.

#### Counter-Example: Sorting a List

- **Input (\(\mathcal{X}\)):** An array of numbers, e.g., [5, 2, 9, 1].
- **Output (\(\mathcal{Y}\)):** The sorted array, e.g., [1, 2, 5, 9].
- **Why NOT ML?**

**Pattern Exists:** Yes, the pattern is clear and deterministic.
- **Data Available:** You could generate infinite training examples.
- **BUT: We CAN Pin It Down Mathematically!** Sorting is a solved problem. Algorithms like QuickSort or MergeSort are provably correct, efficient (\(O(n \log n)\)), and require no data. There is no uncertainty. Using ML here would be absurd—you'd waste computational resources to approximate a function we already know exactly.

## Summary

Machine Learning is the bridge we build when we have **data** and a **goal**, but lack the **formula**. It is a statistical discipline that trades absolute certainty for high-probability correctness, allowing us to automate tasks that were previously the exclusive domain of human intuition.
