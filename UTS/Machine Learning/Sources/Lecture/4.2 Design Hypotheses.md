# Model Design Foundations: From Discrete Vectors to Continuous Spaces

The core problem of building \(\mathcal{H}\) is to design functions. Simply put, this is to describe a mechanism to produce a value for every possible input. This is an abstract problem, and before studying the specific architectural and design ideas, it is helpful to setup some basic notions within a mathematical framework, which will make the many seemingly unmotivated design choices more intuitive and principled.

Generally, the goal is to define a hypothesis space \(\mathcal{H}\), in which members are functions defined over a continuous data space \(\mathcal{X}\). That is, for every possible input \(x\), the model computes an output \(h(x)\). Many core challenges lie in the fact that the input \(x\) varies continuously and leaves too much freedom — Imagine if you need to decide a value of output for \(x=0.123456788\), then for \(x=0.123456789\), ..., the task will be daunting.

## From Discrete Vectors to Continuous Functions

REMARK: the examples can be generated with this hands-on demo notebook: [demo4_2_dis_fn.ipynb](https://canvas.uts.edu.au/courses/42500/files/12974949?verifier=x0xl4m3FWzZKWY2jPFlsC8tcmAMFehTCXRjLICnW&wrap=1)

To get started, let us dramatically reduce how many outputs we need to decide in a problem.

Imagine we partition the continuous space \(\mathcal{X}\) into 100 non-overlapping small regions, say \(U_1, U_2, \ldots, U_{100}\). We can then specify a rule for each \(x \in \mathcal{X}\): if \(x\) falls into the region \(U_i\), then we assign it the value \(a_i\). This way, by specifying just 100 numbers, we have successfully defined a function over an uncountably infinite number of points in \(\mathcal{X}\).

Figure 1: Piecewise-constant functions defined over the unit disc. The disc is partitioned into 100/1,000 Voronoi cells, each assigned a random value in \([-1, 1]\). The function is constant within each cell.

The figure here shows applying this construction to the unit disc. The partition is generated randomly by sampling 100 cell centres uniformly in the disc. Each centre defines a Voronoi cell — the region of points closer to it than any other centre. Each cell is assigned a random value in \([-1, 1]\), and the function is piecewise-constant within each cell. It is not difficult to see that if the partition goes finer and finer, with the number of cells increasing, the resulting function can approximate any arbitrary function with increasing agreement. To the limit, as the number of cells approaches infinity and their size approaches zero, we are back to the original “arbitrary function” family over the input domain as earlier discussed. Therefore, with a finite (and modest, e.g. 100) number of cells, we have a starting point for a simplified function family.

Indeed, when we consider a fixed, finite number of outputs, say 100, this is equivalent to specifying a vector \(\mathbf{a} = [a_1, a_2, \ldots, a_{100}]\), where we only need to decide the value of \(a_i\) for \(i=1, 2, \ldots, 100\).

### A digression to linear algebra: Basis Vectors and Functions as Linear Combinations

Let us take a slightly more careful look at the construction by distinguishing a set of values \(\{a_i\}\) and the vector they represent in the vector space. The value \(a_i\) can be thought of as the coefficient, or weight, associated with a basis vector. A set of basis vectors is a set of fundamental building blocks of a space, such that (let the basis be \(\{\mathbf{f}_1, \mathbf{f}_2, \ldots, \mathbf{f}_{100}\}\) for example):

- 

Every member vector in the space can be expressed as a linear combination of the basis vectors:

\[ \mathbf{f} = a_1 \mathbf{f}_1 + a_2 \mathbf{f}_2 + \ldots + a_{100} \mathbf{f}_{100} \]

for any \(\mathbf{f}\) in the space.

- 

Any basis vector CANNOT be expressed as a linear combination of the other basis vectors. It is impossible to find 99 coefficients \(a_j\) for \(j \neq i\) such that

\[ \mathbf{f}_i \neq a_1 \mathbf{f}_1 + \ldots + a_{i-1} \mathbf{f}_{i-1} + a_{i+1} \mathbf{f}_{i+1} + \ldots + a_{100} \mathbf{f}_{100} \]

### Functions as Vectors in a Function Space

In this example, we treat the function space \(\mathcal{H}\) as a vector space. Each function \(f \in \mathcal{H}\) can be uniquely represented by the coefficients \(\{a_i\}_{i=1}^{100}\) that combine 100 basis functions. What are the basis functions? Technically, they are a (possibly incomplete) set of basis vectors of a vector space of functions. Here in this example, the basis functions are simply the indicator functions \(I_{U_i}(\mathbf{x})\) that output \(1\) if \(\mathbf{x} \in U_i\) and \(0\) otherwise. Graphically, the figure below gives a much more intuitive picture of the basis functions and their linear combination to produce the final function \(f\).

\(a_1 \times\)  \(+\ a_2 \times\) 
\(+\ \cdots\ +\ a_{100} \times\) 
Figure 2: The piecewise-constant function can be expressed as a linear combination of 100 basis functions, each being an indicator function for one of the 100 Voronoi cells. The coefficients \(a_i\) determine the value of the function within each cell.

Essentially, the simplification of function design is achieved by transforming the problem of specifying a value for uncountably infinite points in \(\mathcal{X}\) into the problem of specifying just 100 numbers—a remarkable reduction in degrees of freedom.

Yet the deeper insight is not merely that we have *fewer* degrees of freedom, but that the *choice of basis functions* is what truly determines the character of \(\mathcal{H}\). The 100 numbers \(\{a_i\}\) are just coefficients; it is the 100 indicator functions \(\{I_{U_i}\}\) that decide what kinds of variation the model can and cannot express. The basis shown in the figure is just one toy example, which is illustrative but not very useful in practice. Different choices of basis functions yield fundamentally different hypothesis spaces—and hence different learning biases, generalisation behaviours, and computational trade-offs. As we will see, virtually every major model architecture in machine learning can be understood as a particular answer to the question: *which basis functions should we use to compress the infinite degrees of freedom in the space of functions into finite representations?*

## A Unified Perspective: Basis Functions

A brief summary of the key insight from the above construction is as follows. The piecewise-constant function we just built can be written as a linear combination of 100 simpler, fundamental functions. Let \(I_{U_i}(\mathbf{x})\) be an indicator function that outputs \(1\) if \(\mathbf{x} \in U_i\) and \(0\) otherwise (as shown in the figure). We had discussed that the piecewise-constant function family \(\mathcal{H}\) corresponds to representing any function \(f\) as a linear combination of these indicator functions:

\[ f(\mathbf{x}) = \sum_{i=1}^{100} a_i\, I_{U_i}(\mathbf{x}) \]

These indicator functions \(\{I_{U_1}, \ldots, I_{U_{100}}\}\) form a *basis* for our hypothesis space. It is natural to consider exploring different basis function sets beyond the simple indicator functions \(\{I_{U_i}\}\), which we shall discuss next.

## Different Design Choices for Basis Functions

It is helpful to reckon on the saving we have achieved by using a finite number of basis functions to represent the full (but useless) family of functions over an input domain \(\mathcal{X}\). Essentially, we have restricted the modes in which the output \(Y\) can vary with the input \(X\). They are not allowed to vary in an arbitrary way, but only in the prescribed ways by the bases \(\{\mathbf{f}_i\}\). For example, in the above piecewise-constant function family, if two points \(\mathbf{x}\) and \(\mathbf{x}'\) fall into the same region \(U_i\), then the family does not allow a member function to assign them different output values. ### Local vs Global Basis Functions

Here we have already seen one design choice for the basis functions: each individual basis is supported locally. That is, they care only about a small region of the input space \(\mathcal{X}\), and are zero everywhere else. When combined together into a new function \(\mathbf{f}\), the function \(\mathbf{f}\) processes an input \(\mathbf{x}\) by consulting only one, or a small number of, basis functions which have support at \(\mathbf{x}\), to determine the output \(f(\mathbf{x})\).

The compression of the degrees of freedom in the function space is achieved by having a (few) local mode(s) of variation. As long as the local regions are not too small (meaning we don't need too many of them to cover \(\mathcal{X}\)), we can control the complexity of the model. This philosophy underlies methods like Decision Trees, Finite Element Methods, and certain Kernel Methods.

Alternatively, we can use global basis functions that are non-zero almost everywhere across the entire space \(\mathcal{X}\). However, the basis functions themselves are of simple mathematical form, such as polynomials or trigonometric functions. Hence each basis represents a rigid, stiff mode of variation across the entire input space. The compression of the degrees of freedom is achieved by having only a few global modes of variation. This is often at the cost of losing the ability to capture fine-grained, local variations in the data. A typical classical example of this is the Fourier series representation of functions.

## How is the Data Space \(\mathcal{X}\) Constructed?

Before we move to the common design patterns, there is one interesting, but often overlooked, question: Building learning systems to work on practical problems involves dealing with real-world entities—objects, events, people, physical phenomena, etc. Such raw objects must be transformed into numerical representations before being fed into any processing subroutine (any function implemented on a digital computer). Indeed, in a learning task, the data space \(\mathcal{X}\) consists of abstract mathematical objects, most commonly vectors of real numbers: \(U \subset \mathbb{R}^n\), meaning each entity of interest is represented by \(n\) real numbers of some range.

This perspective leads to a dual understanding of the coordinates \((x_1, \ldots, x_n)\) of \(\mathcal{X}\): to the subsequent functions, they are “stuff” for processing; to the raw entities, they are themselves functions that extract relevant information into a numerical form.

Formally, this leads to two inspiring insights:

### Level 1: Before Modeling (The Physical World)

The data space \(\mathcal{X}\) is not given by nature; it is constructed by us. The real world consists of physical entities or events, which form the **Sample Space \(\Omega\)**. To do machine learning, we must map these abstract entities \(\omega \in \Omega\) into a mathematical space \(\mathcal{X} \subseteq \mathbb{R}^n\).

We do this by defining *observation variables* or *sensors*, which are essentially functions \(X_i: \Omega \to \mathbb{R}\). For example, if \(\omega\) is a patient, \(X_1(\omega)\) might be their blood pressure, and \(X_2(\omega)\) their age. The choice of these sensors makes \(\mathcal{X}\). More specifically, it dictates the geometrical structure of \(\mathcal{X}\), i.e. how the points in \(\mathcal{X}\) are arranged, what is the natural notion of distance between points, and so on.

Hence, the coordinates give a natural set of basis functions—themselves. (Question: Why? Are they local or global in the previous categorization? Verify your thoughts using the demo notebook.) Combining these coordinate functions into a linear combination gives us the classical family of linear models:

\[ f(\mathbf{x}) = w_1 x_1 + w_2 x_2 + \ldots + w_n x_n + b \]

where \(w_i\) are the weights applied to the coordinate functions, and the constant \(b\) can be interpreted as the weight of a special basis function that is always \(1\) (the bias term).

### Level 2: During Modeling (Transformations)

The construction of the data space does NOT necessarily stop at physical sensors. Even without collecting new physical measurements, we can mathematically transform our existing coordinates to create a **new data space**.

Why would we do this? To change the geometry of the problem.

Consider the classic **XOR problem**. In the original 2D coordinate space \(\mathcal{X} = (x_1, x_2)\), the XOR logic cannot be separated by a straight line. The linear perceptron fails because the original “coordinate functions” are insufficient as a basis.

The solution is not to abandon linear models entirely, but to construct a richer data space. If we introduce new, non-linear basis functions—such as \(x_1^2\), \(x_1 x_2\), and \(x_2^2\)—we effectively map our data into a higher-dimensional space where the XOR problem suddenly becomes linearly separable.

This realization—that we can solve complex problems by systematically constructing new, global basis functions—is the starting point for our first major design pattern: **Feature Engineering and Neural Networks**.
