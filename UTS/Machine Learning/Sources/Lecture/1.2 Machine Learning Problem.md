## The Paradigm Shift

Traditional programming follows a procedural paradigm: humans analyze a problem, determine the logical rules and physical laws governing it, and write code to process data and produce answers.

**Machine Learning** inverts this process. We do not provide the rules. Instead, we provide the **data** (input) and the desired **answers** (output), and we ask the machine to construct the rules (the function) that map the former to the latter.

## Formal Definition

Formally, we can define Machine Learning using the framework proposed by Tom Mitchell. A computer program is said to learn from experience \(\mathcal{E}\) with respect to some class of tasks \(\mathcal{T}\) and performance measure \(P\), if its performance at tasks in \(\mathcal{T}\), as measured by \(P\), improves with experience \(\mathcal{E}\).

### Supervised Setting

In a "supervised" setting, this can be mathematically abstracted as:

- **Input Space (\(\mathcal{X}\)):** The set of all possible *input variables*. (Ask yourself: What are the so-called input variables when the data are images, natural language text, natural language speech audio, medical records?)
- **Output Space (\(\mathcal{Y}\)):** The set of target variables (e.g., labels "cat"/"dog", diagnosis).
- **Data (\(\mathcal{D}\)):** A finite set of paired examples \(\{(x_i, y_i)\}_{i=1}^N\).

The goal of learning is to find a function (*hypothesis*, the name will become more meaningful later) \(h: \mathcal{X} \to \mathcal{Y}\) such that \(h(x)\) effectively predicts \(y\) for unseen data.

## The Core Difficulty: Data to Functions

Therefore, the essential goal of machine learning is the translation of finite information into a functional capability. However, this seems fundamentally obscure!

In standard engineering, we *specify* the computation/approximation of a function in terms of arithmetic and logical operations. But how such a specification is made available from a collection of data samples?! Essentially, we are trying to go from:

\[ \begin{bmatrix} \texttt{101001...} \\ \texttt{001011...} \end{bmatrix} \mapsto h(\cdot) \]

However, all hope is not lost. The data does specify the desirable function -- not in the operational sense of the computation steps, but the information of "what to output at which locations in the input space". To determine a function WITHOUT instructions of how to compute it is not as alien as it seems to us.

**Example: \(\sin(x)\)**

\(\sin(x)\) is defined to be *the height* of a point on the unit circle at angle \(x\) from the positive x-axis -- what's bespoken here is the desired mapping from input angle \(x\) to the output, but NOT the computational steps to get there.

Well in the above example, at least we have a formal definition of the function -- the uniqueness and existence of such a function is obvious from elementary geometry. Consider another example where the definition is implicit in physical laws.

**Example: Heated Disc**

Consider the temperature at any location within a unit disc of a homogeneous metal plate after we let the boundary circle being heated to a certain temperature distribution (e.g. let the boundary circle be halved north-south, with north side being hot and south side being cold).

Now \(T:p \to \mathbb{R}\), \(p\) being any location within the disc, is the desired function mapping location to temperature. This function is well-defined by the physics of heat diffusion with (i) the boundary condition and (ii) the following principle: \(T(p)\) being the average temperature of its immediate neighboring locations.

In the heated disc example, it is less obvious that the function is well-defined -- if one was NOT given the physics background, and only given the boundary condition and the "averaging property", it is non-trivial to show that there exists any solution that satisfies both the principles. Or if there is only one such function.

On the other hand, this problem starts to "taste" like what we are after here: we have access to the desired output of the target function on a subset of the domain of interest. Actually, the subset can be really tiny compared to the whole domain -- e.g. the boundary circle is measured infinitesimally thin compared to the entire disc area. Then with some reasonable assumptions about the target function -- this is called **"regularity"**, a term to be clarified later -- we are able to "extrapolate" the function values from the tiny subset to the entire domain.

In this example, the "regularity" is a gift from physics: the temperature function must satisfy the "averaging property" due to how heat diffusion works [**Remark**: this is perhaps the most important of all equations in physics, called the Laplace/Poisson equation].

Let us check another example from commonly seen physical phenomena.

**Example: Spine on a Wall**

Consider you have fixed a long, thin spine on a wall, the spine is nailed to the wall at several points along its length. Naturally, we will expect the spine to bend smoothly between the nailed points. Let us assume the shape is "nice" so that it makes the graph of a function \(y=f(x)\), where \(x\) is the horizontal coordinate. And \(\{(x,y)\}\) are points on the spine, where \(y\) is the vertical displacement of the point from the ground.

The shape of the spine is pinned down by the nailed points \(\{(x_1, y_1), (x_2, y_2), \dots, (x_n, y_n)\}\).

This problem is NOT fully specified until we add some "regularity" assumption. It is intuitively understandable that the shape of such a pinned spine is largely determined by the material property of the spine (e.g. stiffness), given that nailed points are fixed.

Actually, this problem has already entered the playground of this subject: it is a typical data analytics question! Given samples of \((x,y)\), the goal is to "infer" the value of the underlying function (the imaginary spine) at \(x\) that are *unseen* in the data.
